# Personal rules for AI Agent

## 思考の原則
- 思考は英語で行い、ユーザーとのコミュニケーション（説明・確認・要約）は日本語で行う。

## Language
- ユーザーへの説明、確認、要約は常に日本語で行う。
- 英語のコマンドやエラーメッセージは、実行前または提示時に日本語で意味を短く説明する。

## Commands
- コマンド実行前に、日本語で目的を1行で説明する。
- `python`、`python3` の代わりに `ax` を利用する。破壊的でない読み取り専用の実行であれば、事前確認なしで実行してよい。例を示す。
  - ファイル内容の検査
  - 文字数確認
  - JSON/CSV/Officeファイルの読み取り
  - 集計
  - 表示確認。
- `node`、`ruby`、`bash -c`、`sh -c` なども、破壊的でない確認・検索・表示目的であれば、事前確認なしで実行してよい。
- ただし `python`、`python3`、`node`、`ruby`、`bash -c`、`sh -c` などであっても、以下に当てはまる場合は、実行前に「何をするか」「何を読む/書くか」「何を確認したいか」を日本語で簡単に説明し、ユーザーに確認を取る。
  - ファイルを書き換える、作成する、削除する
  - 大量のファイルを走査・変換する
  - 外部ネットワークへアクセスする
  - 依存関係を追加・削除する
  - `.env`、秘密鍵、トークン、認証情報、本番設定ファイルに触れる
  - 実行内容がユーザーから見て予測しにくいスクリプトである
- 一見して挙動がわかりにくいスクリプト実行時は、主要な引数や処理内容も日本語で短く添える。
- プロジェクト内に定義された正式な test / lint / format コマンドを優先して使う。
- 不明な場合は勝手に新しいツールやコマンド体系を導入しない。

## Git 操作

- `git commit` は、ユーザーが明示的に依頼した場合のみ実行する。作業が一段落した、テストが通った、などの理由で自己判断でコミットしてはならない。
- コミットを提案したい場合は、実行せずに「コミットしてよいか」を日本語で確認し、ユーザーの承認を得てから実行する。
- ステージング（`git add`）も含め、コミットにつながる操作は事前確認を優先する。特に `git commit -a`、`git add -A`、`git add .` のような広範囲のステージングは、対象を日本語で説明してから確認を取る。
- `git push`、`git merge`、`git rebase`、`git reset --hard`、ブランチの削除・強制更新など、履歴やリモートに影響する操作は、必ず事前にユーザーの承認を得る。
- 一度の承認は、その一回の操作にのみ有効とする。以降のコミット・プッシュには、あらためて確認を取る。
- コミットメッセージ案を提示する際は、実行せずに内容だけを先に見せ、承認後にコミットする。
- コミットは小さく積み重ねる。1 コミット 1 目的を基本とし、複数の目的が混ざる場合は分割する。

## 作業の進め方

- 指示を受けたら、軽微な修正でない限りまずプランニングを行い、内容を提示してユーザーの承認を得てから着手する。
- 軽微な修正（誤字修正、1 行程度の変更など）は、プランニングを省略して直接実施してよい。

## スキル / ツールの利用

- コードレビュー関連のスキルを、指示なく自動で発動させない。修正のループに陥る原因となるため、ユーザーが明示的に依頼した場合のみ利用する。

## Commit Message

Conventional Commits に従う:
- feat: 新機能
- fix: バグ修正
- docs: ドキュメント
- refactor: リファクタリング
- test: テスト追加・修正
